# 테스트 주도 개발 (TDD) — Java / Gradle / JUnit 5

## 개요

테스트를 먼저 계획한다. 사람의 검토를 받는다. 테스트를 작성한다. 실패를 확인한다. 통과시킬 최소한의 코드를 작성한다. 사람의 검토를 받는다.

**핵심 원칙:** 테스트가 실패하는 것을 직접 보지 않았다면, 그 테스트가 올바른 것을 검증하는지 알 수 없다.

**Human-in-the-Loop 원칙:** AI가 단독으로 사이클을 완결하지 않는다. RED와 REVIEW의 끝은 반드시 사람의 검토다.

**규칙의 문구를 어기는 것은 규칙의 정신을 어기는 것이다.**

---

## 언제 사용하는가

**항상:**
- 새로운 기능
- 버그 수정
- 리팩터링
- 동작 변경

**예외 (사용자에게 확인 필요):**
- 일회성 프로토타입
- 자동 생성된 코드
- 설정 파일

---

## 절대 법칙

```
실패하는 테스트 없이 프로덕션 코드를 작성하지 말 것
RED Plan을 사람이 검토하기 전에 테스트 코드를 작성하지 말 것
GREEN 코드를 사람이 검토하기 전에 다음 사이클을 시작하지 말 것
```

---

## Red-Green-Review 사이클

```
┌─────────────────────────────────────────────────────┐
│  RED                                                 │
│  1. Plan.md 에 테스트 계획 작성                        │
│  2. ★ 사람에게 검토 요청 (필수 — 여기서 멈춘다)          │
│  3. 승인 후 테스트 코드 작성                            │
│  4. 실패 확인 (기능 부재로 실패해야 함)                  │
└──────────────────┬──────────────────────────────────┘
                   │ 올바르게 실패
                   ▼
┌─────────────────────────────────────────────────────┐
│  GREEN                                               │
│  1. 통과시킬 최소 구현 작성                             │
│  2. 테스트 통과 확인                                   │
│  3. 전체 테스트 회귀 확인                               │
└──────────────────┬──────────────────────────────────┘
                   │ 전체 GREEN
                   ▼
┌─────────────────────────────────────────────────────┐
│  REVIEW                                              │
│  1. 테스트 코드 + 구현 코드 + 실행 결과 제시             │
│  2. 정리 제안 (중복, 이름, 추출 후보) 제시               │
│  3. ★ 사람에게 검토 요청 (필수 — 여기서 멈춘다)          │
│  4. 승인 후 정리 적용 + 다음 RED 시작                   │
└─────────────────────────────────────────────────────┘
```

---

## RED — 테스트 계획 및 작성

### Step 1: Plan.md 작성

테스트 코드를 쓰기 전에 **반드시** Plan.md에 계획을 작성한다.

```markdown
## Cycle N — RED Plan

### 테스트할 동작
(무엇을 검증할 것인가 — 한 문장)

### 이 테스트가 지금 필요한 이유
(왜 이 순서인가 — 이전 사이클과의 관계)

### 예상 테스트 구조
- 테스트 메서드 이름: `동작을설명하는이름()`
- Given: (사전 조건)
- When: (실행)
- Then (EXPECT): `assertEquals(기대값, 실제값)`

### 예상 실패 이유
(기능이 없어서 실패해야 함 — 예상 오류 메시지)
```

### Step 2: ★ 사람에게 검토 요청 (필수)

Plan.md 작성 후 **반드시 멈추고** 검토를 요청한다:

> **"[Cycle N] RED Plan을 작성했습니다. Plan.md를 검토해 주세요.  
> 승인하시면 테스트 코드를 작성하겠습니다."**

**검토 없이 테스트 코드를 작성하지 않는다. 예외 없음.**

### Step 3: 테스트 코드 작성 (승인 후)

```java
@Test
@DisplayName("동작을 한국어로 설명한다")
void 동작을설명하는이름() {
    // Given
    Game game = new Game();

    // When
    game.roll(0);  // ...

    // Then
    assertEquals(0, game.score());
}
```

**요구사항:**
- 하나의 동작만
- `@DisplayName`으로 한국어 의도 표현
- 실제 코드 사용 (mock 사용 금지, 불가피한 경우 제외)

### Step 4: RED 확인

```bash
./gradlew test --tests "bowling.GameTest.메서드이름"
```

확인할 것:
- 테스트가 실패하는가 (컴파일 오류가 아닌)
- 실패 메시지가 Plan에서 예상한 그대로인가
- **기능이 없어서** 실패하는가 (오타·누락이 아닌)

**컴파일 오류?** → 최소 스텁을 만들고 올바르게 실패할 때까지 다시 실행. 컴파일 오류는 RED가 아니다.

## GREEN — 최소 구현

테스트를 통과시킬 **가장 단순한** 코드를 작성한다.

```java
// 통과시킬 만큼만
public int score() {
    return 0;
}
```

**금지:**
- 지금 필요 없는 기능 추가
- 다른 코드 리팩터링
- 테스트가 요구하는 것 이상의 "개선"

### GREEN 확인

```bash
# 방금 작성한 테스트만
./gradlew test --tests "bowling.GameTest.메서드이름"

# 전체 회귀 확인 (필수)
./gradlew test
```

확인할 것:
- 새 테스트가 통과하는가
- **기존 테스트가 모두 여전히 통과하는가**

**다른 테스트가 깨졌다?** → 지금 고쳐라. 다음으로 넘어가지 마라.

---

## REVIEW — 검토 및 정리

### Step 1: 결과 제시

다음을 사람에게 보여준다:

1. **작성한 테스트 코드**
2. **작성한 구현 코드**
3. **테스트 실행 결과** (PASSED 확인)
4. **정리 제안** (있다면): 중복, 이름, 추출 후보

### Step 2: ★ 사람에게 검토 요청 (필수)

반드시 **멈추고** 검토를 요청한다:

> **"[Cycle N] GREEN이 확인됐습니다. 구현 코드를 검토해 주세요.  
> • 정리할 부분이 있으면 말씀해 주세요.  
> • 다음 사이클로 진행해도 되면 승인해 주세요."**

**검토 없이 다음 RED를 시작하지 않는다. 예외 없음.**

### Step 3: 정리 적용 (승인 후, 해당하는 경우)

그린 상태를 유지하면서:
- 중복 제거
- 이름 개선
- 헬퍼 / private 메서드 추출

정리 후 전체 테스트 재확인:

```bash
./gradlew test
```

## Plan.md 형식

프로젝트 루트에 `Plan.md`를 두고, 각 사이클마다 내용을 추가한다.

```markdown
# TDD Plan

## Cycle 1 — RED Plan

### 테스트할 동작
거터 게임(모든 투구 0)의 점수는 0이다.

### 이 테스트가 지금 필요한 이유
가장 단순한 케이스. Game 클래스의 기본 API(roll, score)를 확인한다.

### 예상 테스트 구조
- 메서드 이름: `gutterGameScoresZero()`
- Given: `Game game = new Game()`
- When: `game.roll(0)` × 20
- Then: `assertEquals(0, game.score())`

### 예상 실패 이유
`score()`가 -1을 반환해 `0 != -1`로 실패.

---

## Cycle 1 — REVIEW

### 테스트 코드
...

### 구현 코드
...

### 실행 결과
GameTest > 거터 게임의 점수는 0이다 PASSED

### 정리 제안
없음.
```

## Gradle / JUnit 5 실용 명령어

```bash
# 단일 테스트 실행
./gradlew test --tests "bowling.GameTest.메서드이름"

# 전체 테스트
./gradlew test

# 캐시 무시하고 재실행
./gradlew test --rerun-tasks

# 상세 로그
./gradlew test --info

# 리포트 위치
# build/reports/tests/test/index.html
```

`build.gradle.kts` 최소 설정:

```kotlin
plugins { java }

repositories { mavenCentral() }

dependencies {
    testImplementation("org.junit.jupiter:junit-jupiter:5.10.0")
    testRuntimeOnly("org.junit.platform:junit-platform-launcher")
}

tasks.test {
    useJUnitPlatform()
    testLogging { events("passed", "skipped", "failed") }
}
```

## 흔한 합리화

| 변명 | 현실 |
|------|------|
| "Plan 없이 바로 테스트 쓰면 되지" | Plan 없이 쓴 테스트는 무엇을 검증하는지 불명확하다. 계획이 먼저다. |
| "REVIEW 건너뛰고 바로 다음 사이클 시작하면 빠르지 않나" | 빠르게 쌓인 코드는 느리게 무너진다. REVIEW가 다음 사이클의 품질을 결정한다. |
| "사람이 바빠서 기다리기 싫다" | 검토 없는 TDD는 TDD가 아니다. 기다려라. |
| "테스트하기엔 너무 단순하다" | 단순한 코드도 깨진다. 테스트는 30초면 된다. |
| "사후 테스트도 같은 목표를 달성한다" | 사후 = "이 코드가 무엇을 하는가?", 우선 = "무엇을 해야 하는가?" |
| "X시간을 지우는 것은 낭비" | 매몰비용 오류. 검증되지 않은 코드를 두는 것이 기술 부채다. |

## 위험 신호 — 멈추고 처음부터 다시 시작

- Plan.md 없이 테스트 코드를 작성했다
- RED Plan 검토 없이 테스트 코드를 작성했다
- REVIEW 검토 없이 다음 사이클을 시작했다
- 테스트보다 먼저 작성된 구현 코드
- 테스트가 즉시 통과 (이미 존재하는 동작을 테스트하는 것)
- 테스트가 왜 실패했는지 설명할 수 없음
- "이번 한 번만" 검토를 생략했다

**이 모든 것의 의미: 코드를 삭제하라. TDD로 처음부터 다시 시작하라.**

---

## 검증 체크리스트

**RED**
- [ ] Plan.md에 이번 사이클 계획이 작성됐다
- [ ] 사람이 Plan을 검토하고 승인했다
- [ ] 테스트가 예상한 이유로 실패한다 (기능 부재)

**GREEN**
- [ ] 최소한의 코드로 테스트를 통과시켰다
- [ ] 전체 테스트가 통과한다 (`./gradlew test`)

**REVIEW**
- [ ] 테스트·구현 코드와 실행 결과를 사람에게 제시했다
- [ ] 사람이 검토하고 다음 사이클을 승인했다
- [ ] 정리 사항이 있다면 적용 후 전체 테스트 재확인

---

## 최종 규칙

```
Plan → 사람 검토 → 테스트 작성 → RED 확인
최소 구현 → GREEN 확인 → 사람 검토 → 다음 사이클
```

**RED와 REVIEW에서 사람의 검토 없이 다음 단계로 넘어가는 것은 절대 금지다.**
